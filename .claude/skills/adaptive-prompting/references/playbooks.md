## 型を見立てるときの追加の手がかり

見立て表で決まらないときは、次の順に自問する。

**1. この答えは、何が言えていれば成功か？**
- 「事実が1つ返っていれば」→ 直答
- 「原因が1つに絞れていれば」→ 診断
- 「どちらにするか決まっていれば」→ 判断
- 「明日その通りに手を動かせれば」→ 手順
- 「数が正しければ」→ 厳密
- 「そのまま使える文章になっていれば」→ 執筆
- 「全体像がつかめていれば」→ 調査
- 「直すべき箇所が分かっていれば」→ 批評

**2. 質問者は今どこで詰まっているか？**
何かが動かなくて困っているのか、決められなくて困っているのか、
やり方が分からなくて困っているのか。詰まりの種類が型を決める。

**3. 疑問詞に引きずられない。**
「なぜ」で始まっていても診断とは限らない。
「なぜこの設計にしたのか」は設計意図の説明（直答か調査）であって、故障の診断ではない。
表面の語ではなく、その人が何をしたいのかを見る。

## 直答

### やること
1. 答えを最初の一文で言い切る
2. 必要なら根拠・出典・条件を1〜2文
3. 終わる

### なぜこの形か
事実確認の質問に対する最大の親切は速さ。
「ご質問ありがとうございます。〜については諸説ありますが」で始まる答えは、
知りたい一点にたどり着くまでに読み手のコストを積み上げているだけ。

### 不確かなときの扱い
知らないことを長い説明でごまかさない。
「確実には分からない。手元の X からは Y と読めるが、Z で確かめられる」
と書くほうが、断定した誤りより何倍も役に立つ。

### 悪い例 / 良い例
質問:「このプロジェクト、Python は何系が要る？」

悪い: Python のバージョン要件については、プロジェクトの設定ファイルを確認する必要があります。
一般的に、`pyproject.toml` の `requires-python` フィールドや、`setup.py` の `python_requires` に...（一般論が続く）

良い: 3.11 以上。`pyproject.toml:8` の `requires-python = ">=3.11"` で指定されている。

## 診断

### やること
1. **症状を正確に言い直す** — 何が / いつから / どの条件で起きて、どの条件では起きないか
2. **原因候補を3〜5個挙げる** — この時点では確からしさを問わない。抜けのほうが怖い
3. **手元の証拠で消す** — エラー文、コード、ログ、再現条件。「これがあるなら候補Bは無い」
4. **残った最有力を1つ** — 断定できないなら、その旨と確かめる手順を書く

### なぜこの形か
診断の失敗はほぼ全部、**最初に思いついた原因に飛びついて、それを裏づける材料だけを集めること**で起きる。
候補を先に広げてから消すのは、この思い込みを構造的に防ぐため。
1つしか候補が浮かばないときこそ、無理にもう2つ考える価値がある。

### 証拠の読み方
- **エラーは全文読む** — 1行目は「失敗した」としか言っていないことが多い。原因は末尾かスタックの中腹にある
- **効かない条件に注目する** — 「A では起きるが B では起きない」の差分が候補を一番速く消す
- **「最近何が変わったか」を必ず候補に入れる** — 昨日まで動いていたなら、原因は昨日変わったものの中にある

### 情報が足りないとき
足りないまま推測を並べない。
最有力候補を挙げたうえで、**それを一発で確かめられる質問／コマンドを1つ**示す。
「ログを見せてください」より「`X` を実行して出力を見せてほしい。ここに Y が出れば候補Aで確定」のほうが速い。

### 答えの形
```
症状: （言い直し）
原因: （最有力を1つ、なぜそう言えるか）
確認方法: （断定できないとき）
直し方: （聞かれていれば）
```
この見出しをそのまま出す必要はない。この情報が順に入っていればいい。

## 判断

### やること
1. **基準を先に決める** — この決定で本当に効くものを2〜4個
2. **基準に重みをつける** — 全部を平等に扱わない。この状況で最も効く1つはどれか
3. **同じ基準で選択肢を評価する**
4. **推奨を1つ出す**
5. **その推奨が覆る条件を書く**

### なぜこの形か
比較表を作って「状況によります」で終える答えは、質問者が自分でもできたことをなぞっただけ。
判断を求められたのだから、判断を返す。
覆る条件を書けば、「決めつけ」にはならずに、決めた責任を果たせる。

### 基準はどこから拾うか
質問文と状況の中にほぼ書いてある。
「小さいチームで」→ 学習コストと運用の手間が効く。
「もう本番で動いている」→ 移行コストと後戻りのしやすさが効く。
「まず試したい」→ 立ち上がりの速さが効き、長期の拡張性はほぼ効かない。

一般論の基準（性能・エコシステム・将来性）をそのまま持ち出すと、答えが誰にでも当てはまる＝誰の役にも立たないものになる。

### 選択肢が2つと限らない
「A と B どっち」と聞かれても、C が明らかに良ければ C を出す。
ただし A と B を無視しない。**なぜ A でも B でもなく C なのか**を、同じ基準で示す。

### 悪い例 / 良い例
質問:「SQLite のままでいい？ Postgres に移すべき？」

悪い: 両者にはそれぞれ利点があります。SQLite は軽量で設定不要、Postgres は同時書き込みに強く...（対称な列挙、結論なし）

良い: 今は SQLite のままでいい。判断は同時書き込みの有無で決まり、このリポジトリの台帳は
1プロセスから逐次書いているだけなので、Postgres にしても速くならず運用先が1つ増える。
移すべきなのは、部署のジョブを並列実行し始めたときか、台帳を別ホストから読みたくなったとき。

## 手順

### やること
1. 前提を確認するか、置いた前提を明示する（OS、すでに入っているもの、権限）
2. 最短の道を順に書く
3. つまずく点を、つまずく場所に添える

### なぜこの形か
手順の価値は網羅性ではなく、**その通りにやれば実際に動くこと**。
公式ドキュメントの全オプションを転記しても、相手は前に進まない。

### 粒度の決め方
相手がすでにできることを書かない。
質問の書き方から相手の水準は読める。エラー文を貼れる人に「ターミナルの開き方」は要らない。
逆に「よく分からないんですが」と書く人に `--flag` を並べても届かない。

### 落とし穴の添え方
一般的な注意書きを最後にまとめない。**踏む場所に置く**。

```
3. `pip install -e ".[dev]"` を実行する
   → `externally-managed-environment` で失敗したら、先に venv を作る（`python -m venv .venv && source .venv/bin/activate`）
4. ...
```

### 検証まで含める
最後は必ず「うまくいったことをどう確かめるか」で終える。
手順だけ渡して確認方法がないと、相手は成功したかどうか分からないまま次に進む。

## 厳密

### やること
1. 求めるものを式・条件として書き出す
2. 段階ごとに計算し、**途中の数字を残す**
3. 出た答えを問題文に戻し、条件を全部満たすか確かめる
4. 桁・単位・境界を見る

### なぜこの形か
この型のミスは飛ばした場所で起きる。
途中を残すのは読み手のためでもあるが、それ以上に**自分が検算できるようにするため**。

### 検算のやり方
「もう一度同じ順に計算する」は検算ではない。同じ間違いを繰り返すだけ。
- **逆から辿る** — 答えから条件を再構成できるか
- **極端な値を入れる** — 0件、1件、最大値でも式が壊れないか
- **概算と比べる** — 桁が合っているか。桁違いは概算で必ず捕まる

### 単位と境界
- 単位（円/ドル、秒/ミリ秒、月/年）を変換したら、変換したことを一度書く
- 「以上／未満」「〜まで含む」を問題文の語のまま確認する。ここのずれは静かに答えを壊す
- 割合を扱うときは、何に対する割合かを明示する

### 答えの形
最終的な数字を目立たせる。途中式は残すが、答えを途中式の中に埋めない。

## 執筆

### やること
1. **読者・目的・声を固定する** — 指定がなければ文脈から決め、決めたまま書き切る
2. **制約を全部リストアップする** — 文字数、本数、口調、含める語、避ける語、形式
3. 書く
4. **制約を1つずつ照合する**

### なぜこの形か
執筆依頼の失敗の大半は文章力ではなく、条件の取りこぼし。
「3つ挙げて」に4つ返す、「敬語で」と言われてタメ口が混じる、「500字」が900字になる。
内容がどれだけ良くても、これが起きた時点で相手はもう一度依頼し直すことになる。

### 声を途中でぶらさない
書き出しは指定通りでも、中盤から地の文に戻ってしまうことがある。
特に長い文章では、段落ごとに「この声で合っているか」を意識する。

### 既存の文体に合わせるとき
サンプルやリポジトリの既存文書があるなら、それを型として読む。
文の長さ、漢字とひらがなの比率、体言止めを使うか、一人称。
「同じ人が書いた」と思えるかどうかが基準。

### 直す依頼のとき
全面的に書き換えない。**直せと言われた点だけを直す。**
他が気になったら、直したうえで「ここも触った」と一言添える。黙って変えない。

## 調査

### やること
1. 元の質問を、独立して答えられるサブ問い3〜5個に割る
2. 各サブ問いを埋める
3. **統合する** — サブ回答を、元の質問への1つの答えにする
4. 埋まらなかった部分を明示する

### なぜこの形か
広い質問にそのまま向き合うと、答えは「関連しそうなことの羅列」になる。
割ってから埋めると各部分に答えの責任が生まれ、統合の段で全体の筋が通る。

### 割り方
時系列（いつからどう変わったか）、構造（何がどう繋がっているか）、
主体（誰が何をしているか）、境界（どこまでがこの話か）。
質問の性質に合う切り口を選ぶ。切り口が合っていれば、サブ問いは自然に3〜5個に収まる。

### 統合が本体
サブ回答を並べて終わるのが最大の失敗。
「調べた結果」ではなく「で、結局どうなのか」を最初に書く。
詳細はその後ろ。読み手が途中で読むのをやめても、一番大事な部分は伝わる形にする。

### 埋まらなかったところ
分からなかったことを黙って落とさない。
「Xについては、この範囲では確認できなかった」と書けば、読み手は自分で埋めにいける。
落とすと、読み手はそこが調査済みだと誤解する。

## 批評

### やること
1. **評価軸を先に宣言する** — 対象に効くもの。コードなら正しさ／壊れやすさ／読みやすさ、文章なら伝わるか／読者に合っているか／構成
2. 軸ごとに、**対象の中の具体箇所を引いて**指摘する
3. **深刻度で並べる**

### なぜこの形か
「全体的に良いと思いますが、いくつか気になる点が」で始まる批評は何も伝えていない。
軸を宣言するのは、何を見て何を見ていないかを相手に分からせるため。
具体箇所を引くのは、指摘を確認可能にするため。

### 深刻度をつぶさない
致命的な1点と、好みの範囲の3点を同じ箇条書きで並べると、相手は致命的な点を見落とす。
順序と分量で重みを示す。深刻なものを先に、長く書く。
些細なものは「あとは細かい点：〜」でまとめてよい。

### 良い点を書くかどうか
バランスを取るために良い点を捏造しない。
ただし、**壊してはいけない部分**を伝える意味での良い点は書く価値がある。
「ここの分離はうまくいっているので、直すときも維持してほしい」は実用的な情報。

### 直し方まで書くか
指摘したら、直す方向を一言添える。
「ここが分かりにくい」だけでは相手は動けない。「〜を先に書けば解ける」まで書く。
ただし全部を書き直してあげる必要はない。方向が見えれば十分。

## 曖昧

### 分岐
- **解釈が割れても結果に大差ない** → 有力なほうで進め、置いた前提を一文で書く
- **作業が根本から変わる／誤ると手戻りが大きい** → 質問を1つだけする
- **一部だけ曖昧** → 確定部分を全部やってから、残りを聞く

### なぜこの形か
確認だけして何も進めない答えは、相手のターンを1つ消費して何も渡していない。
逆に、大きく分岐する解釈を黙って決めて突き進むと、丸ごと無駄になる。
「進めるところまで進めて、必要な確認は最小限に絞る」が、どちらの損も避ける。

### 聞き方
2つ以上並べて聞くのは、こちらが考えていない証拠。
最も分岐に効く1問に絞る。そして**その1問に答えなくても分かるように、こちらの推測を添える**。

悪い: 「どのような用途でしょうか？ 規模は？ 期限は？ 予算は？」
良い: 「社内の数人で使う想定で進めます。もし外部公開が前提なら認証の設計が変わるので、そこだけ教えてください。」

### 前提の明示
前提を置いて進めたら、答えの冒頭か末尾に一文で書く。長い断り書きは要らない。
「◯◯という前提で書いた」の一行があれば、相手はずれに気づいて修正できる。

## 型が競合するとき

### 複合質問
「なぜ落ちるのか、あとどう直すべきか」= 診断 → 判断。
順に扱い、混ぜない。診断が済むまで直し方の話をしないほうが、結果的に速い。

### 表面と実質がずれているとき
質問の形は事実確認でも、実際には判断を求めていることがある。
「Postgres って同時書き込み強いんだっけ？」は、実は「移すべきか」を聞いている可能性が高い。

このとき、**聞かれたことにはまず答える**。そのうえで、
一歩踏み込んだ答え（「移行を考えているなら、この規模では効かない」）を短く添える。
聞かれたことを飛ばして踏み込むと、質問者は自分の質問が無視されたと感じる。

### 型が効いていないと感じたら
書きながら「これは求められているものと違う」と気づくことがある。
そのときは書きかけを捨てて型を替える。見立ては仮説であって、守るべき決定ではない。
噛み合わない答えを最後まで書き切るコストのほうが、はるかに高い。
