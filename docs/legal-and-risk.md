# 規約・法務・リスク

自動化そのものより、**自動化した結果として外に出るもの**にリスクがあります。
運用を始める前に一度は目を通してください。ここに書いた内容は法的助言ではありません。
判断に迷う場合は各社の最新の規約と、必要なら専門家に確認してください。

---

## 1. note へのブラウザ自動投稿（最大のリスク）

note には記事投稿用の公開 API がありません。そのため自動投稿は必然的に
ブラウザ操作（`src/note_shop/publish/browser.py`）になります。

**このコードは既定で動きません。** 動かすには `--i-accept-tos` を明示的に付ける必要があります。

判断材料:

- 多くのサービスの利用規約は、自動化されたアクセスやスクレイピングを制限しています。
  **note の利用規約の最新版を自分で読んで判断してください。** 規約違反はアカウント停止に
  つながり、この事業では在庫（記事）ごと失うことを意味します。
- UI 変更で簡単に壊れます。壊れたことに気づかず「投稿できたつもり」になるのが最も危険です。
- 実装は**下書き保存までしか行いません**。公開・価格設定は意図的に未実装です。
  誤った価格での公開や、有料ラインのずれによる本文流出は取り返しがつきません。

**推奨する運用は、`out/<slug>/` の成果物を人間が貼り付けることです。** 1本あたり3分程度で、
リスクはゼロになります。自動投稿で削れるのはこの3分だけで、失うものは事業全体です。

## 2. X / Threads の API

| 項目 | 注意点 |
|---|---|
| X の Recent search | 有料プラン向け。プランによって取得期間・回数が変わる |
| X の投稿 | アプリ専用 Bearer トークンでは投稿できない（ユーザー権限のトークンが必要） |
| X の予約投稿 | API にネイティブの予約機能がない。本実装は自前のキュー + cron で代替 |
| Threads のキーワード検索 | `threads_keyword_search` 権限が必要。未審査アプリでは失敗する |
| 自動投稿の頻度 | 各社ともスパム的な自動投稿を禁止している。1記事3本・時間帯分散が既定値の理由 |

いずれも取得・投稿に失敗した場合は例外を投げずに警告を出して続行します。
**失敗が黙って握りつぶされないよう、ログは必ず残る場所に出してください。**

## 3. AI 生成物であることの扱い

- **生成AIで書いた記事であることを隠す必要はありませんが、隠す設計にもしないでください。**
  検品担当は「AIっぽい言い回しを人の文章に直す」工程であって、
  AI が書いた事実を偽装する工程ではありません。
- プラットフォームによっては AI 生成コンテンツの表示ポリシーがあります。note の
  最新のガイドラインを確認してください。
- 生成物の著作権・権利関係の扱いは、利用する API の利用規約に従います。

## 4. 書いてはいけないこと（生成レベルで禁止している）

`config/company.yaml` の `company.prohibitions` は、全部署のシステムプロンプトに
そのまま制約として渡されます。既定で入れているもの:

| 禁止事項 | 理由 |
|---|---|
| 再現性のない収益実績の断言 | 景品表示法上の優良誤認・誇大表示のリスク |
| 投資・医療・法律の個別具体的な助言 | 各業法（金商法・医療法・薬機法・弁護士法など）に触れうる |
| 出典のない統計値の記載 | AI が最も事実誤認を生みやすい箇所 |

扱う領域によっては追加が必要です。例:

- 健康・美容を扱うなら → 効果効能の断定表現（薬機法）
- 副業・収入を扱うなら → 「誰でも」「確実に」といった表現（特商法・景表法）

### PR・アフィリエイトを含める場合

広告であることを隠した投稿はステルスマーケティング規制の対象になります。
集客ポストにアフィリエイトリンクや案件を含める運用にするなら、
`company.prohibitions` ではなく、営業担当のプロンプト側に**表示義務のルールを足してください**。
現状の実装は広告を含まない前提です。

## 5. 他人のコンテンツの扱い

- リサーチ担当が集めるのは**傾向の把握のため**です。集めたポストの文面を記事に転載しないでください。
- 執筆担当が参照する「売れた記事」は**自社の記事のみ**です（DB に入っているのは自社記事だけ）。
- 「過去のレター」も自社が配信したものを置いてください。

---

## 6. 認証情報の管理

`.env` は `.gitignore` に入っています。以下は**絶対にコミットしないでください**:

- `ANTHROPIC_API_KEY`
- `X_BEARER_TOKEN` / `X_ACCESS_TOKEN`
- `THREADS_ACCESS_TOKEN` / `THREADS_USER_ID`
- `NOTE_EMAIL` / `NOTE_PASSWORD`

アソシエイトのトラッキングIDは秘密情報ではない（リンクに出る）ため `config/company.yaml` に置きます。
アソシエイトのログイン情報はこのリポジトリでは一切扱いません。

とくに note のログイン情報は、漏れると記事も売上も失います。ブラウザ自動投稿を使わないなら
**そもそも設定しないでください**。使わない鍵は、置かないのが最も安全です。

---

## 7. 事故ったときに戻れるようにしておく

- `data/noteshop.db` に企画・本文・売上のすべてが入っています。定期的にバックアップを取ってください
- `out/` は再生成できますが、公開済み記事の本文はここにしか残りません
- どちらも `.gitignore` に入っています（機密と生成物をリポジトリに混ぜないため）

## 8. Amazonアソシエイト（`affiliate:` を有効にする前に）

アフィリエイト担当（`src/note_shop/affiliate.py`）は既定で無効です。
以下は実装の前提にした注意点ですが、**規約・運用ルールは改定されます。有効化の前に、
アソシエイト・プログラム運営規約と note のガイドラインの最新版を自分で確認してください（すべて要確認）。**

| 項目 | このリポジトリでの扱い |
|---|---|
| 広告であることの表示（ステマ規制） | 本文の最上部に `pr_label` を必ず入れる。最初のリンクより前に無ければ書き出しを止める |
| アソシエイトの開示文 | `disclosure` を本文冒頭に入れる。無ければ書き出しを止める |
| 価格の掲載 | 載せない。リンクと同じ行に価格があれば書き出しを止める |
| 商品の選定 | 人間が登録した台帳からのみ。AIに ASIN や商品名を作らせない |
| 未検証の商品 | 既定で載せない。載せる場合も「未検証」と明記する |
| 商品情報の自動取得（PA-API 等） | 使っていない。利用条件（実績要件など）と提供状況は変わるため、使うなら最新の公式情報を確認 |
| Amazon のページの自動取得（スクレイピング） | 実装しない。規約違反のリスクが高い |
| メール・PDF などへのリンク掲載 | しない。`data/letters` のレターや配布物にリンクを貼らないこと（規約で制限がある想定・要確認） |
| リンクを載せる場所の登録 | note のアカウントURLなど、リンクを載せる場所をアソシエイト側に登録しておく（要確認） |

### 自動化しないもの

- **紹介料の取得は手動ダウンロード + `noteshop affiliate import`。** レポート取得のためにアソシエイトの
  管理画面へ自動ログインする実装は、note の自動投稿と同じ理由（規約・アカウント停止リスク）で入れていません。
- **集客ポストに Amazon リンクは入れません。** X / Threads の告知は note への誘導だけにしています。
  SNS にリンクを直接載せたい場合は、PR表記の自動付与を営業担当に追加してから行ってください。

### 審査について

アソシエイトは、申請後一定期間内に一定の販売実績が無いと承認されない仕組みがあります
（条件は要確認）。**記事が少ない段階で有効化しても審査を通らない可能性が高い**ので、
note の販売が回り始めてから有効化することを推奨します。
